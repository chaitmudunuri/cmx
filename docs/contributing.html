Contributing to CMX

CMX is pre-1.0 and shaped by the people who use it. Bug reports, platform testing and ideas are all genuinely useful — you do not need a finished patch to start.

Good first contributions#

These are the highest-value things you can do right now, in rough order of usefulness:

  1. Test a build on Linux or Windows. Neither platform has a prebuilt binary and no maintainer coverage. Open an issue with your distribution, desktop environment and what broke — even "it works" is data.
  2. Report an editor-fidelity bug. Vim motions, CodeMirror behaviour and large-file handling are where a careful user finds edge cases.
  3. Find a search regression. Workspace search is subtle: .gitignore handling, binary files, very long lines and cancellation are easy to get wrong.
  4. Improve the documentation. If something confused you, it will confuse the next person.
  5. Recapture a screenshot. Follow the capture guide.

Looking for an open problem? The issue tracker is the source of truth.

Roadmap#

The next release milestone is v0.2.0 — packaging for all three platforms: a macOS universal binary, published Linux and Windows installers, code signing, notarization and release checksums. After that: language-server support in v0.3.0, and a plugin API in v0.4.0.

The full roadmap is ROADMAP.md, including what CMX deliberately will not do and why.

Development setup#

Node 20+ with pnpm, Rust stable, and the WebKitGTK toolchain on Linux. Full instructions are on the developer setup page.

git clone https://github.com/chaitmudunuri/cmx.git
cd cmx
pnpm install
pnpm tauri dev

Pull requests#

  1. Branch off main — git checkout -b fix/vim-word-motions.
  2. Keep the diff focused. Unrelated cleanups make review slower for everyone; send them separately.
  3. Run the checks: npx tsc --noEmit, pnpm build, cargo test.
  4. Fill in the PR template and link the issue with Fixes #123.
  5. Commit messages are imperative and capitalized: Fix tab close preserving sibling scroll position.

For a larger change, open an issue first so the approach can be agreed before the work is done. Review is best-effort and may take a few days.

Reporting bugs#

Include your CMX version, OS and architecture, what you expected, what happened instead, and minimal reproduction steps. Use the bug report template. Questions that are not bugs belong in Discussions.

Security issues#

Please do not open a public issue for a security problem. Report it privately through GitHub's security advisory form. The scope and the response time are set out in the repository's SECURITY.md.

Community#

Everyone participating is expected to follow the Code of Conduct, which is adapted from the Contributor Covenant.
